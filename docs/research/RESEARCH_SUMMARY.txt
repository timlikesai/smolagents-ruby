CONFIGURATION PATTERN RECOMMENDATION
====================================

Three-Tier Configuration Hierarchy (Industry Standard):

Highest Priority: Environment Variables
  ENV['OPENAI_API_KEY']              # Secrets only
  ENV['SMOLAGENTS_RETRY_ATTEMPTS']   # Deployment overrides

Middle Priority: Rails Credentials
  Rails.application.credentials.smolagents.openai_api_key

Lowest Priority: Block Configuration
  Smolagents.configure { |config| config.retry_attempts = 3 }

Implementation:
- Add Smolagents.configure { |c| } block support
- Auto-load from ENV with SMOLAGENTS_ prefix
- Support Rails credentials.yml.enc
- Load from config/smolagents.yml (environment-specific)
- All sources merge with ENV taking precedence

ASYNC/BACKGROUND JOBS PATTERN RECOMMENDATION
=============================================

Hybrid Approach (Recommended by RubyLLM author for LLM workloads):

For LLM Operations: Use Async/Fibers
  - I/O-bound work (99% waiting for tokens)
  - Lightweight, thousands run on few connections
  - Example: Async::Job with Async do...end

For CPU-Bound Work: Use Sidekiq
  - Data processing, calculations
  - Thread pool efficient
  - Example: ApplicationJob

Reasoning:
  Traditional thread pools waste resources on I/O wait:
  - 1000 concurrent LLM ops = 1000 threads = 1000 DB connections (99% idle)
  
  Fibers solve I/O-bound problem:
  - 1000 concurrent fibers = 1 thread = few DB connections
  - User-space cooperative scheduling
  - Perfect for streaming token scenarios

Rails Integration:
  - Sidekiq for existing jobs
  - Async for new LLM jobs
  - ActionCable for real-time updates
  - Background job = stream tokens to WebSocket

TESTING UTILITIES RECOMMENDATION
=================================

Already Excellent - Just Document Better:

MockModel: Pre-populated responses, simulates API behavior
  Smolagents::Testing::MockModel.new(
    responses: ['tool_call(...)', 'final_answer(...)'],
    delay: 0.1,
    track_calls: true
  )

Matchers: RSpec assertions for agent behavior
  expect(agent).to have_run_tool(:search)
  expect(agent).to have_completed
  expect(agent).to have_completed_in_steps(5..10)

Scenarios: Test case builder with conditional responses
  scenario.when_tool_called(:search).then_return("results")

Behavior Tracer: Record what agent did
  tracer.steps, tracer.tools_used, tracer.duration, tracer.tokens_used

VCR Integration: Record/playback HTTP cassettes
  VCR.use_cassette('gpt4_response') { model.generate(...) }

ERROR HANDLING AND RESILIENCE RECOMMENDATION
=============================================

Current smolagents-ruby: Excellent Foundation
  ✓ Circuit breaker: .with_circuit_breaker(threshold: 5)
  ✓ Retry: .with_retry(max_attempts: 3)
  ✓ Fallback: .with_fallback(backup_model)
  ✓ Health checks: .with_health_check(cache_for: 5)
  ✓ Rate limiting: RateLimiter with multiple strategies
  ✓ Dead Letter Queue: Automatic retry of failed calls
  ✓ Events: RetryRequested, FailoverOccurred, ErrorOccurred, etc.

Recommendation: Add Error Classification
  Problem: Different errors need different handling
    - Network errors: Retry with exponential backoff
    - Rate limit: Retry with longer backoff (10+ seconds)
    - Auth error: Fail immediately, alert team
    - Validation error: Fail immediately, fix input

  Solution: ErrorClassifier
    retriable?(error) -> true/false
    backoff_for(error) -> { initial_delay, exponential_base, max_delay }
    alert_on?(error) -> true/false

PRODUCTION DEPLOYMENT RECOMMENDATION
====================================

Before Going Live: Checklist

Configuration:
  [ ] API keys in environment/credentials (not source code)
  [ ] Retry policy set (max_attempts >= 3)
  [ ] Fallback model configured
  [ ] Timeout values appropriate (30s connection, 120s streaming)
  [ ] Rate limiting enabled

Observability:
  [ ] Logging enabled with structured JSON format
  [ ] Health check endpoint at /health
  [ ] Metrics endpoint exposed (if using Prometheus)
  [ ] OpenTelemetry configured (if using distributed tracing)
  [ ] Error alerting configured (Sentry, PagerDuty, etc.)

Reliability:
  [ ] Circuit breaker enabled with appropriate threshold
  [ ] Health checks running regularly (every 30 seconds)
  [ ] Dead letter queue monitored (for manual retries)
  [ ] Fallback model tested and verified working
  [ ] Error handling tested with various failure scenarios

Security:
  [ ] No API keys in logs
  [ ] Request validation enabled
  [ ] Rate limiting per-user/IP
  [ ] Audit logging for sensitive operations
  [ ] Secrets rotation plan

Testing:
  [ ] Unit tests with mock models
  [ ] Integration tests with real models (recorded via VCR)
  [ ] Load testing to find breaking points
  [ ] Cost estimation complete
  [ ] Canary deployment plan ready

Key Metrics to Monitor:
  - Agent completion time (p50, p95, p99)
  - Error rate by type
  - Model fallover frequency
  - Cost per request
  - Tokens used distribution
  - Queue depth (if using background jobs)
